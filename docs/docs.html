Documentationfor Strata 0.8.

Strata maps your information systems in 3D: each site is a stack of plates (zones), coloured by VLAN, holding its assets, the flows between them, what they expose, their vulnerabilities and the people to call. It runs on your own server.

Install with Docker

You need Docker with the Compose plugin, about 1 GB of RAM and 1 GB of disk. To build the image yourself, the host also needs access to the npm registry during the build.

git clone https://github.com/SolidGeeks/strata.git
cd strata
cp .env.example .env
nano .env                         # set EDIT_PASS
docker compose up -d --build      # builds the image here

On Windows: copy .env.example .env then notepad .env.

Or skip the build: docker compose pull && docker compose up -d fetches the ready-made image ghcr.io/solidgeeks/strata of the release. Every image is signed; check it before deploying with gh attestation verify oci://ghcr.io/solidgeeks/strata:0.8.0 --owner SolidGeeks, which must print Verification succeeded!

Open http://localhost:8080 and sign in with EDIT_USER / EDIT_PASS. The map starts empty: Load demo (5 IS) fills it with five sample sites, Delete everything clears it.

docker compose logs -f strata     # logs
docker compose restart strata     # restart
docker compose down               # stop (data stays in the volume)

By default the port only listens on the machine itself (127.0.0.1:8080). See HTTPS and network to open it to your users.

HTTPS and network

Passwords travel as HTTP Basic credentials. Never expose Strata over plain HTTP beyond the machine it runs on.

Bundled proxy (Caddy)

  1. In .env, set SITE_ADDRESS=strata.example.lan, the name your users will type.
  2. Point that name at the host (internal DNS or hosts file).
  3. Start with the HTTPS profile:
docker compose --profile https up -d

Add TRUST_PROXY=private to .env, so that failed sign-ins are counted per user rather than for Caddy as a whole.

The Caddyfile uses tls internal: Caddy signs the certificate with its own local authority, which suits an internal network or a VPN. Install that authority on your workstations to remove the browser warning:

docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./caddy-root.crt

For a public name reachable on ports 80 and 443, delete the tls internal line and Caddy gets a Let’s Encrypt certificate itself.

Your own reverse proxy

Proxy to http://127.0.0.1:8080. Live updates use Server-Sent Events on /api/events, so turn buffering off on that path. With nginx:

location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
location /api/events {
    proxy_pass http://127.0.0.1:8080;
    proxy_buffering off;
    proxy_read_timeout 1h;
}

Set TRUST_PROXY=loopback so that Strata reads the client address from X-Forwarded-For. Only trust a proxy that sets this header itself.

Strata also works under a sub-path (https://intranet/strata/): it only uses relative URLs.

Without Docker (systemd)

Node.js 20 or later. The server has no npm dependency at run time; npm run setup only copies three.js and the fonts into public/vendor.

sudo mkdir -p /opt/strata && sudo cp -r strata/* /opt/strata/
cd /opt/strata
sudo npm run setup
sudo useradd --system --home /opt/strata --shell /usr/sbin/nologin strata
sudo mkdir -p /var/lib/strata && sudo chown strata:strata /var/lib/strata
sudo cp .env.example /etc/strata.env && sudo chmod 600 /etc/strata.env
sudo cp deploy/strata.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now strata

The service listens on 127.0.0.1:8080: put an HTTPS reverse proxy in front. For a quick try on a workstation: npm run setup && EDIT_PASS=test npm start.

Building from source elsewhere: npm ci (the lockfile pins three.js 0.128 and the fonts), npm run vendor (copies them into public/vendor), npm test, then ship package.json, server/, public/ and scripts/users.mjs and run node server/server.js. Nothing is downloaded at run time, and nothing is written outside DATA_DIR; data files are readable by the server’s own user only.

Nix and NixOS

The repository is a flake. To try Strata (data in ./data, listening on 127.0.0.1:8080):

EDIT_PASS=test nix run github:SolidGeeks/strata

On NixOS, the module runs it as a hardened systemd service: its own strata user, data in /var/lib/strata, read-only system, no capabilities, restricted system calls.

{
  inputs.strata.url = "github:SolidGeeks/strata";

  outputs = { nixpkgs, strata, ... }: {
    nixosConfigurations.myhost = nixpkgs.lib.nixosSystem {
      modules = [
        strata.nixosModules.default
        {
          services.strata = {
            enable = true;
            settings = {               # the variables of Configuration
              EDIT_USER = "admin";
              TRUST_PROXY = "loopback";
            };
            secretFiles.EDIT_PASS = "/run/secrets/strata-admin";  # out of the Nix store
            openFirewall = false;      # keep it behind an HTTPS reverse proxy
          };
        }
      ];
    };
  };
}

Files in secretFiles are read by systemd as root and handed to the service as credentials, so they can stay root-only. environmentFile takes KEY=value lines the same way. Accounts from the command line: sudo -u strata env DATA_DIR=/var/lib/strata strata-users set alice contributor. modules = [ ./my-connector ] provides connector modules; settings.MODULE_REGISTRY = "off" keeps to them. The flake also has overlays.default, and its checks build the package (with the tests) and run a NixOS VM test of the module.

Accounts and roles

RoleCan
viewerread the map, sheets, plans and history
contributoralso prepare proposals (drafts) and submit them; import a firewall configuration file as a proposal
approveralso edit the map directly, approve or reject proposals, restore versions, run connectors
adminalso manage accounts and connector settings

Manage accounts in the app (Collaboration › Account) or on the command line; the server picks changes up within seconds. Passwords are hashed with scrypt in data/users.json.

docker compose exec strata node scripts/users.mjs list
docker compose exec strata node scripts/users.mjs set alice contributor   # asks for a password
docker compose exec strata node scripts/users.mjs role alice approver
docker compose exec strata node scripts/users.mjs disable alice

Repeated failed sign-ins are refused for a while (429), per account and per client address (see Configuration). Only different wrong passwords count, so a tab left open with an old password locks nobody out, and browsers already signed in keep working.

For single sign-on (Entra ID, LDAP…), put an authentication proxy in front and create the same account names.

Building the map

Sites, zones, VLANs

An information system (IS) is a site. Zones, contacts sets its zones (one level each, for example Industrial, Office, Core IT, Exposed), its VLANs with their ranges, and the IS contacts shown on assets that have none of their own. Arrange plates lets you drag a plate anywhere on its level; Line up puts a level back in a row.

Assets

Each asset has a type (server, firewall, router, switch, workstation, PLC…), a VLAN, an IP, a system, applications with their listening ports, vulnerabilities, a criticality, incident contacts and notes. A new asset starts on the first free IP of its VLAN range; an IP outside the range is pointed out. A vulnerability has a CVSS score or a severity, and optionally an EPSS (0 to 1, or a percentage) and a Known exploited (CISA KEV) mark. Search by name or IP to fly to it.

Flows

A flow goes from a source to a destination on a port: assets, the Internet, or a named Internet service. Strata suggests the devices it crosses (edge firewall for Internet traffic, core firewall or router between VLANs); untick Suggested to set the path yourself. Exposure follows from the flows: a port is Internet, inter-VLAN or intra-VLAN depending on where its traffic comes from.

Every flow crossing a firewall, router, switch or gateway has its own lane on that device, in 3D and in 2D. Flows › Colour by colours them by risk, by exposure, or Per flow: flows that cross the same device then never share a colour (up to 10). On a device sheet, Flows crossing this equipment lists them in lane order; hovering one picks it out on the model.

Moving around the 3D view

Drag with the left button to orbit, with the middle (or right) button to move the view left, right, up and down, and scroll to zoom. On a touch screen, one finger orbits, two fingers zoom and move. The view stops at the edge of the model; Reset view centres it again.

2D diagram

The 2D diagram view is the same model, flat: drag assets and plates, draw a flow from one asset to another (F), add an asset on a plate (A), move (V). Positions are shared with the 3D model.

Theme

Display › Theme: Auto follows the system, Day and Night force it. N switches.

Views and business services

The switch at the top of an IS gives three points of view:

  • Physical: the 3D model and the 2D diagram.
  • Application: one box per application (Nginx, Tomcat, PostgreSQL…) with the assets it runs on, and arrows for the flows between applications, from the one that sends them to the one listening on their port. Workstations and other pure clients are grouped by type and VLAN.
  • Business: the business services of the IS, and everything each one relies on.

A business service is an activity of the organisation: online sales, payroll, production line 1. Add one in the Business view (+ Business service) with a criticality, an owner and only the assets it runs on; an asset form also ticks the services it runs. Strata works out the rest from the flows: the assets they call, and so on, the equipment these flows cross and the equipment in front of the service, and the Internet services they use. Log and monitoring flows (syslog, SNMP traps, NetFlow) are left out. Show on the model picks a service out in 3D or 2D.

The asset sheet lists the business services impacted by an asset, and why: it runs on it, it relies on it through a chain of flows (web-01 → app-erp → db-erp), or its flows cross that equipment.

Risk priorities

Analysis › Risk priorities gives one score per asset, from 0 to 100, and the vulnerabilities to fix in order. The score multiplies three factors, each between 0 and 1:

FactorHow it is computed
VulnerabilitiesFor each one, its severity (CVSS / 10) times its likelihood of exploitation: 1 when it is on the CISA list of known exploited vulnerabilities, otherwise 0.15 + 0.85 × √EPSS, otherwise 0.3. Combined as the chance that at least one gets exploited.
ContextThe average of the exposure (Internet 1, inter-VLAN 0.7, intra-VLAN 0.45, none 0.3) and the reachability from the Internet along the flows (1 for one hop, 0.1 less for each extra hop, at least 0.5; 0.3 when not reachable).
CriticalityThe higher of the asset’s own and that of the business services it would hit: low 0.5, medium 0.75, high 1.

Critical from 70, high from 40, medium from 20. The fixes are ordered by the score each vulnerability would give its asset on its own. Remediation list (CSV) exports the whole list. On the asset sheet, Risk score › Why? shows each factor.

Strata does not download the EPSS and KEV feeds: it works offline. They come from the Cyberwatch connector, an import, or the asset form.

Attack paths and blast radius

Analysis › Attack paths lists the critical assets (criticality High, of their own or through a business service) that an attacker coming from the Internet could reach along the allowed flows, with every path to each one, most likely first. Where to cut names the assets and the equipment that every path to a critical asset goes through: harden those, or tighten their rules. The rest of the model fades; hovering a path picks it out, in 3D and 2D.

Blast radius starts from any asset instead (pick it in the panel, or Blast radius on its sheet): everything an attacker holding it could reach, the most likely way to each asset, and the business services hit.

StepLikelihood of taking the next asset over
VulnerableIts vulnerabilities, combined as for the risk score (CVSS times likelihood of exploitation).
Remote administration port50%: SSH, Telnet, RPC, SMB, RDP, VNC, WinRM, for credentials picked up on the way.
Any other service10%, for what the last scan did not see.

A step counts for the highest of these, and a path for the product of its steps. Flows run one way: answering a flow does not let the destination reach back. Both lists export as CSV.

Proposals and history

A contributor clicks Propose a change, then edits as usual: everything goes into a draft (blue Draft bar) and the live map does not move. Submit for review sends it to the approvers. A proposal can also start from a JSON file: a whole-map export, or one IS exported with Export this IS (JSON).

The approver opens it from Proposals: the map shows the changes in place (green added, amber modified, dashed red for removed flows in 2D) with the full list. They comment, then Approve and publish or Reject. Nobody approves their own proposal unless ALLOW_SELF_APPROVAL=true. If the same items changed on the map meanwhile, the approver is warned and decides.

Every change is recorded (who, when, what) in data/history.jsonl. History › View shows the map as it was, read-only; Restore brings the whole map back to that version, and the restore is itself a version you can undo.

Internet services

Instead of a single “Internet” cloud, describe the destinations you allow: ESET update servers, Ubuntu mirrors, Windows Update, NTP, your SaaS. Each service has hosts (FQDN or IP) and ports, and is either shared by every IS or specific to one. Flows can start or end at a service; services appear next to the cloud in 3D, at the top of the 2D diagram and in plans, and the firewall rules export uses their hosts as destinations.

Connectors

In Collaboration › Connectors. An admin fills in each connector’s settings; Test the connection checks access; Sync now (approver) runs it in the background; Sync automatically every … hours schedules it. Connectors never write the map: each run prepares one proposal per IS, refreshed in place while it is still open. When the map already matches, no proposal is created.

Credentials are stored in data/connectors.json (mode 600), never sent back to browsers. For internal certificates, paste your CA in More settings, or tick Accept any TLS certificate on a trusted network. Assets remember their record in each tool (ext), so later syncs still match after a rename.

Cyberwatch

Reads the server list and each server’s CVEs (API v3). Matches assets by host name, then IP. Lowest severity and maximum per asset are configurable; CVEs ignored in Cyberwatch are left out by default. Cyberwatch owns the CVE-… entries of the assets it scans; findings typed by hand are kept. EPSS and the CISA KEV mark are read when Cyberwatch gives them. Create a read-only API key in Profile › API keys; Basic authentication is the default, the older HMAC signature is available for older instances.

GLPI

Reads computers, network devices, printers and phones through apirest.php (GLPI 9.5 and 10): IP addresses from network ports, operating system, installed software, technician and group in charge, location. The location picks the IS, with rules such as Lyon = lyon or /^DC-?West/ = dcw, otherwise the IS whose name appears in it. Existing assets get their system, applications and contacts (entries typed by hand stay); missing assets are created on the VLAN whose range holds their IP, or on a “To sort” plate. Enable the REST API, create an API client (App-Token) and a read-only service account with a user token.

phpIPAM

Reads sections, subnets, VLANs and addresses (/api/{app}/, phpIPAM 1.4+). A subnet already used as a VLAN range goes to that IS; otherwise rules on the section, location or description decide. Creates or completes VLANs (new ones arrive in an Imported zone), fills asset IPs, moves an asset to its subnet’s VLAN, and lists differing IPs without changing them. Create an API application with Read rights and SSL with App code token security.

Palo Alto

Two sources: a configuration file exported from the firewall or Panorama (Import a configuration file, open to contributors), or the XML API with a read-only key. Active allow rules become flows of the chosen IS:

  • address objects and groups → assets by IP; a range expands into its assets up to a threshold (12 by default);
  • public addresses and FQDNs → an existing Internet service with the same host, or a new one;
  • services and service groups → ports; application-default → the usual ports of common App-IDs;
  • any in an untrust, internet, outside or wan zone → the Internet;
  • the chosen firewall as the device crossed; Internet-to-admin or database ports flagged as risky.

What cannot be drawn (internal any→any, dynamic groups, negations, addresses with no asset) is listed in the proposal. Flows from a rule that disappeared are removed; flows drawn by hand are never touched. A proposal from a file counts as the importer’s own for the four-eyes rule.

Modules and the module store

Each connector is a module: a folder with a manifest (its settings, whether it imports files, what it may reach) and its code. The four above ship with Strata. Administrators add others from Connectors › Module store: each module shows what it reads (the map, the network) before you install it, and the store checks each package against the checksum it publishes. Three to start with: CSV inventory imports the assets of an IS from a spreadsheet saved as CSV (columns name, ip, type, os, role, vlan, criticality, notes); Nmap scan imports a scan saved with -oX (hosts that are up, the system Nmap guessed, open ports as listening ports of the applications); both are open to contributors. NetBox syncs devices, virtual machines, VLANs and prefixes with a read-only token, a NetBox site going to an IS through rules such as Lyon HQ = lyon.

Every test or run starts the module in its own process: it reads its own folder only, not the data files, the accounts or the other connectors’ settings; it cannot write files or start programs; it sees none of the server’s variables; it is stopped after CONNECTOR_TIMEOUT_MINUTES. It can use the network, so install only modules you trust. Modules installed from the store can be removed from their card; modules you provide yourself go in MODULES_DIR (or services.strata.modules on NixOS). Writing one, and publishing it in the store: MODULES.md.

Try them without your tools

Load the demo, then start the simulator (fake Cyberwatch, GLPI, phpIPAM and PAN-OS on port 8099, with data matching the Lyon site) and use the addresses and credentials listed at the top of the script:

docker compose exec -d strata node scripts/connector-sim.mjs

Plans and exports

  • Architecture plan of an asset, as PNG or SVG, light whatever the theme. One right-angle line per flow, numbered, with the table of its flows (path, port, volume, exposure) and of the firewall rules the asset needs under the drawing. Scope: the asset’s own flows, or every path from and to the Internet. Filters: inbound, outbound, crossing; Internet, inter-VLAN, intra-VLAN. Colour: by exposure, or per flow.
  • Architecture file of an IS (Analysis › Architecture file, or the IS summary), in the order audits and security accreditation files follow: cover and sign-off table, summary, scope, network diagram, zones and VLANs, applications, asset inventory, flow matrix, the rules each firewall needs, exposure, vulnerabilities and remediation order, attack paths, plans of the exposed and critical assets, incident contacts, change history, method. One standalone HTML file that prints to A4 PDF.
  • Flow matrix and firewall rules of an asset as CSV (a generic table, to map to your firewall’s object names).
  • Remediation list of an IS as CSV, from Risk priorities.
  • 2D diagram as SVG.
  • Export JSON: the whole map, or one IS, to back up, move or edit elsewhere and bring back as a proposal.

Backups

To undo a mistake, use History › Restore. Backups are for losing the server. Strata copies db.json into /data/backups/ at start, every BACKUP_EVERY_HOURS, before each import and before each restore, and keeps the latest BACKUP_KEEP.

./scripts/backup.sh                                          # backups/strata-YYYYMMDD-HHMMSS.tar.gz: map, history, proposals, accounts, connectors
./scripts/restore.sh backups/strata-20261024-120000.tar.gz   # everything back
./scripts/restore.sh export.json                             # the map only

The archive contains the connector credentials: store it like a secret. Include it, or the strata-data volume, in your usual backup.

Upgrading

./scripts/backup.sh
git pull                      # or replace the files, keeping .env
docker compose up -d --build  # or: docker compose pull && docker compose up -d

Coming from IS Map 3D (0.5.0 or older): the service is now strata and the volume strata-data. To keep your data, find the old volume with docker volume ls (usually is-map_ismap-data), add DATA_VOLUME=is-map_ismap-data to .env, then docker compose down --remove-orphans && docker compose up -d. IS Map exports, backups and API scripts keep working.

API

Every route uses the same credentials as the interface, with the rights of the account’s role. Writes need the headers Content-Type: application/json and X-Requested-With: strata. Group several writes into one history entry with X-Batch and X-Batch-Label. For a tool that should propose rather than write, give it a contributor account and use POST /api/proposals.

Security and licence

This map describes your weak points precisely: treat it as sensitive data.

  • Keep it on an internal network or behind a VPN, over HTTPS, with a long unique EDIT_PASS.
  • Give everyone a named account with the lowest role that does the job: every change is attributed in the history.
  • The server sends strict security headers (CSP with no external script, no framing, no referrer) and refuses cross-site writes.
  • Connectors: use read-only service accounts, limited to the Strata server’s IP where the tool allows it.
  • Connector modules run in their own restricted process, but can use the network: install only modules you trust. The store checks each package’s checksum; uploading packages is off by default.
  • Repeated failed sign-ins are refused for a while; behind a reverse proxy, set TRUST_PROXY.
  • Data files are readable by the server’s own user only. Passwords can come from files (EDIT_PASS_FILE), out of the environment.
  • Published Docker images are signed: check them with gh attestation verify (see Install).

Known limits

  • Storage is a single JSON file, fine for a few thousand assets.
  • Authentication is HTTP Basic; for SSO, use an authentication proxy.
  • Two approvers editing the same IS directly at the same moment: the last save wins (history lets you go back). Proposals detect conflicts.
  • Connectors follow the public API documentation of each tool and were tested against simulators: test, sync, and read the first proposal carefully. GLPI 11’s new API (/api.php/v2) is not supported yet.
  • Palo Alto: NAT rules, security profiles, dynamic address groups and the Panorama device-group hierarchy are not interpreted.
  • draw.io and Visio imports are not supported: only Strata JSON exports become proposals.
  • Business dependencies follow the recorded flows: a dependency with no flow on the map is not seen.
  • The risk score uses the EPSS and KEV values recorded on each vulnerability; Strata does not fetch them. A vulnerability is not tied to a port, so any open flow to its asset counts.
  • Attack paths only follow the recorded flows, and the likelihoods are estimates: an exploit chain, a stolen account or a flow missing from the map can go further. Paths of up to 8 steps are searched, and up to 20 are listed per critical asset.
